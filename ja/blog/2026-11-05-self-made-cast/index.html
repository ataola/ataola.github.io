自分で作るキャストシステム——既存プロトコルを使わなかった理由

郑江涛 · 2026-11-05 · 4 分 · 投屏 / Android / 工程笔记

ベンダーのキャストは課金、Miracast は当たり外れ、DLNA はストリームしか飛ばせない。結局二週間かけて自作した。プロトコル設計、遅延、そしてハマりどころの記録。

この記事は現在中国語のみです。

家里有台投影仪，想把手机画面投上去。试过一圈现成方案，各有各的别扭：厂商投屏要会员、Miracast 兼容性玄学、DLNA 只能投流不能投屏。最后干脆自己写了一套——手机抓屏编码推流，投影仪收流解码。

这篇不贴代码，只记设计取舍和踩过的坑。

一、先把问题拆开

投屏本质是四件事：

  1. 采集：拿到屏幕画面（Android 的 MediaProjection）
  2. 编码：H.264 硬编，音频 AAC
  3. 传输：局域网，Wi-Fi 抖动大
  4. 播放：低延迟解码 + 铺满屏幕

前两步是标准 API，难的是第三、四步——延迟、抖动、丢包。

二、协议：13 字节帧头 + 两个端口

没有用 RTP，因为需要控制的字段太少，自己定更简单：

[4B 长度][1B flags][8B ptsNs][payload]

flags:
  0x01 视频关键帧
  0x02 音频
  0x04 配置
  0x08 ping
  0x10 HELLO
  0x20 拒绝
  • TCP 19602 走配置和关键帧，保证不丢
  • UDP 19603 跑视频，用 FEC 抗丢包
  • 控制信令（配对、抢占、停止）单独一个端口 19601

为什么关键帧走 TCP：丢一个 I 帧，后面几秒都是花屏。宁可慢一点，也不能烂画面。

三、延迟是怎么降下来的

  • 不做缓冲队列：解码器只保留最新一帧，宁可丢帧也不堆延迟
  • 按需丢帧：发送端读编码器输出队列长度，超过阈值就丢非关键帧
  • 自适应码率：按 RTT 和发送失败率动态调，20Mbps 一路降到 4Mbps
  • 按机型限码率：老设备编 20Mbps 直接卡死，得给每台机器一个上限

实测同一局域网，手机到投影仪的单向延迟在 15–25ms 量级，操作是跟手的。

四、坑都集中在「设备差异」上

代码本身不难，难的是每台设备都不一样：

  • 编码器初始化失败要能降级重试（不同厂商的 MediaCodec 差异极大）
  • 投影仪只有 32 位 ABI，装了 64 位包直接失败
  • 老机型内存小，解码器一开就 OOM
  • 投屏中如果另一个 App 抢了前台，会直接断流——需要会话隔离和踢旧逻辑

经验：凡是「系统级能力」，一定要按「设备 × 系统版本」列矩阵实测，不要相信 API 文档。

五、另一个坑：媒体文件不一定是你以为的格式

顺手做过一个曲库整理工具，遇到一件有意思的事：从某个 App 目录里拷出来的 .ts 文件，扩展名是 MPEG-TS，但一解码就报错：

top block unavailable for requested intra mode -1

看首字节就明白了——正常的 MPEG-TS 每 188 字节有一个 0x47 同步头，而这些文件的首字节是随机的：

e6 d9 b8 4b 8e 8f 8d 29   ← 不是明文

文件是加密的，只有那个 App 自己的本地文件服务会边读边解密。于是换个思路：不去硬啃加密算法，而是让它自己的服务把明文吐出来——把它的本地 HTTP 端口转发到本机，按文件 ID 请求一遍，拿到的就是解密后的流。

这件事的启发：遇到加密，先找「谁有权读它」，别硬啃算法。

六、最后

这套东西现在日常在用：手机点一下就连，投影仪顶上显示帧率、码率、分辨率，卡的时候一眼能看出是哪一段的问题。

自己写的好处不是性能，而是每一层都看得见——出问题能定位到帧、到包、到编码器参数，而不是对着一个黑盒猜。
